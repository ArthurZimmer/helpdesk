1. ARQUITETURA TÉCNICA (STACK)
================================================================================

Armazenamento de Arquivos:
- AWS S3 ou Google Cloud Storage

Emails Transacionais:
- SendGrid, AWS SES ou Resend
- Para notificações automáticas

2. MODELO DE DADOS (5 TABELAS PRINCIPAIS)
================================================================================

2.1. USERS (Usuários)
---------------------
- id (primary key)
- nome
- email (unique)
- senha_hash
- role (CLIENTE ou AGENTE)
- created_at

2.2. CATEGORIES (Categorias)
----------------------------
- id (primary key)
- nome (ex: "Financeiro", "Técnico", "Comercial")
- descricao
- created_at

2.3. TICKETS (Chamados)
-----------------------
- id (primary key - número sequencial ex: #1001)
- user_id (foreign key → Users - quem abriu)
- assigned_to (foreign key → Users - agente responsável)
- category_id (foreign key → Categories)
- status (enum)
- assunto
- descricao
- created_at
- updated_at

2.4. MESSAGES (Comentários/Interações)
--------------------------------------
- id (primary key)
- ticket_id (foreign key → Tickets)
- user_id (foreign key → Users - quem escreveu)
- mensagem (text)
- created_at

2.5. ATTACHMENTS (Anexos)
-------------------------
- id (primary key)
- message_id (foreign key → Messages - NOT NULL)
- url (caminho no S3/GCS)
- filename (nome original do arquivo)
- size (tamanho em bytes)
- created_at

NOTA IMPORTANTE: Anexos sempre pertencem a uma mensagem específica. 
Ao criar um ticket com anexo, cria-se automaticamente a mensagem inicial.

3. MÁQUINA DE ESTADOS (FLUXO DE STATUS)
================================================================================

FLUXO PRINCIPAL:
NOVO → EM_ANALISE → AGUARDANDO_CLIENTE → RESOLVIDO → FECHADO
  ↓
CANCELADO (para tickets duplicados/erro)

DESCRIÇÃO DOS ESTADOS:
----------------------
1. NOVO: Estado inicial quando o cliente cria o ticket

2. EM_ANALISE: Agente assume o ticket (atribuição manual ou automática)

3. AGUARDANDO_CLIENTE: Agente respondeu e aguarda retorno (SLA pausa aqui)

4. RESOLVIDO: Agente marcou como solucionado

5. FECHADO: Cliente confirmou OU sistema fechou automaticamente após X dias 
   sem resposta (tickets fechados não podem ser editados)

6. CANCELADO: Ticket descartado (duplicado, engano) - não conta nas métricas 
   de resolução

TRANSIÇÕES PERMITIDAS:
----------------------
- De RESOLVIDO → EM_ANALISE (se cliente reabrir por insatisfação)
- Qualquer status → CANCELADO (apenas agentes)

  autenticação SPF/DKIM

  celular)

✓ Backup Automático: Rotina diária de backup do PostgreSQL

7. FLUXOS DE USUÁRIO PRINCIPAIS
================================================================================

7.1. FLUXO: CLIENTE ABRE TICKET
--------------------------------
1. Cliente faz login
2. Acessa dashboard
3. Clica em "Abrir Novo Chamado"
4. Preenche formulário:
   - Assunto
   - Descrição
   - Categoria
   - Anexos (opcional)
5. Submete ticket
6. Sistema cria ticket com status NOVO
7. Sistema cria mensagem inicial automaticamente
8. Sistema envia email de confirmação ao cliente
9. Cliente é redirecionado para visualização do ticket

7.2. FLUXO: AGENTE RESPONDE TICKET
-----------------------------------
1. Agente faz login
2. Visualiza fila de tickets NOVO
3. Seleciona ticket
4. Sistema muda status para EM_ANALISE
5. Agente atribui ticket para si
6. Agente escreve resposta
7. Agente adiciona anexos (se necessário)
8. Agente muda status para AGUARDANDO_CLIENTE
9. Sistema envia email ao cliente notificando resposta

7.3. FLUXO: RESOLUÇÃO DE TICKET
--------------------------------
1. Agente marca ticket como RESOLVIDO
2. Sistema envia email ao cliente
3. Cliente pode:
   a) Confirmar resolução → Status muda para FECHADO
   b) Reabrir ticket → Status volta para EM_ANALISE
   c) Não responder → Sistema fecha automaticamente após X dias

7.4. FLUXO: BUSCA E FILTROS (AGENTE)
------------------------------------
1. Agente acessa dashboard
2. Utiliza filtros rápidos:
   - Meus Chamados
   - Não Atribuídos
   - Atrasados
   - Por Categoria
3. OU utiliza campo de busca por ID/palavra-chave
4. Sistema exibe resultados filtrados
5. Agente seleciona ticket para gerenciar

9. REQUISITOS ADICIONAIS
================================================================================

9.1. SISTEMA DE SLA (Service Level Agreement)
----------------------------------------------
- Rastreamento de tempo de resposta
- Pausa de SLA quando status = AGUARDANDO_CLIENTE
- Indicador visual de tickets atrasados
- Métricas de performance

9.2. SISTEMA DE LOGS E AUDITORIA
---------------------------------
- Registro de todas as alterações em tickets
- Histórico de mudanças de status
- Histórico de atribuições
- Histórico de mudanças de categoria
- Timestamp e usuário responsável por cada ação

9.3. SISTEMA DE PERMISSÕES
---------------------------
- CLIENTE: Pode criar tickets, visualizar seus próprios tickets, 
  adicionar mensagens, reabrir tickets resolvidos
- AGENTE: Todas as permissões de cliente + atribuir tickets, 
  alterar status, alterar categoria, cancelar tickets, 
  visualizar todos os tickets

9.4. VALIDAÇÕES E REGRAS DE NEGÓCIO
------------------------------------
- Tickets fechados não podem ser editados
- Apenas agentes podem cancelar tickets
- Apenas o cliente pode confirmar resolução
- Sistema fecha automaticamente tickets resolvidos após X dias sem resposta
- Rate limiting: máximo 10 tickets por hora por usuário
- Validação de tipos de arquivo permitidos para anexos
- Validação de tamanho máximo de anexos
